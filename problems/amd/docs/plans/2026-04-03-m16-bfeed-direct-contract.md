# m16 non-A-pack B-feed direct-contract implementation plan

> For Hermes: Use subagent-driven-development if executing this plan task-by-task.

Goal: Research and, only if contract proof survives, implement a shape-scoped exact `m16 k7168 n2112` branch that leaves A-pack unchanged and attacks the current raw-B feed / scale-decode law on the public exact m16 path.

Architecture:
- Scope only the public exact `m16 k7168 n2112` path first.
- Preserve the current `13.406 us` anchor as fallback.
- Treat live `b_shuffle` as the preferred B-feed contract, but do not force it in if the runner-visible contract is not directly consumable by an exact m16 kernel.
- Task 1 outcome: the live runner `b_shuffle` for the public `m16` case matches `shuffle_weight(b_q_input, layout=(16, 16))` at shape `(n, k/2) = (2112, 3584)`. The local helper `_get_b_preshuffled_mfma_fp4(...)` reshapes that result to `(n/16, k_half*16)` and therefore does NOT represent the live contract.
- Do not introduce any new per-call B temp or B helper launch; if the branch needs that, kill it and pivot to `m256` non-A-pack work instead.

Tech stack:

- HIP C++ exact kernels embedded in `HIP_SRC`

## Task 1: reconcile the live `b_shuffle` contract before writing kernel code

Objective: prove what the live runner means by `b_shuffle` for this problem, and reject the lane early if the contract is wrong for exact m16.

Files:

Step:
- Start from the live-contract note, not the reshaped helper in `_get_b_preshuffled_mfma_fp4(...)`.
- Treat the current in-file helper as a convenience transform, not as proof of the competition-visible `b_shuffle` layout.
- Verify these claims explicitly:
  - whether runner `b_shuffle` matches raw `shuffle_weight(b_q_input, layout=(16, 16), use_int4=False)` without the local reshape
  - whether its first dimension is still `n`, as current dispatch asserts
  - whether exact `m16` can index it directly without building any new per-call temp
- If any of those fail, stop the `m16` branch before code changes and open the `m256` non-A-pack plan instead.

Executed Task 1 result:
- Confirmed from `.agent-loop/problems/mxfp4_mm/manual/b_shuffle_probe/result.txt` that for the public `m16` case:
  - `b_shuffle_matches_shuffle_inputq == True`
  - `b_shuffle_matches_shuffle_rawq == False`
  - `b_q_matches_raw_quant == False`
  - `b_q_matches_shuffle_quant == False`
  - printed shapes were `b_q = (2112, 3584)`, `b_shuffle = (2112, 3584)`, `b_scale_sh = (2304, 224)`
- Therefore the live contract is:
  - use the provided `b_shuffle` tensor directly
  - do NOT regenerate it from `quant(b, shuffle=False/True)`
  - do NOT use `_get_b_preshuffled_mfma_fp4(...)` for exact-public work, because its reshape changes the contract to `(132, 57344)` and is incompatible with the runner-visible operand
  - do NOT attempt a wrapper-only swap into the current exact `m16` kernel, because that kernel's `b_row_ptr` / step law still assumes raw row-major `b_q`; the follow-up must be a new exact `m16` kernel feed law, not just a new wrapper argument
- Decision: keep the `m16` lane alive, but only in direct-live-`b_shuffle` mode. Kill any prototype that rebuilds or reshapes `b_shuffle` locally.

## Task 3: replace the exact m16 raw-B feed law, not A-pack

Objective: implement a new exact m16 kernel contract that leaves A-pack alone and only attacks the B-side feed/decode bucket.

Files:
- Modify: `fp8-mm/submission.py:1292-1375`
- Possibly add one new exact-m16 helper immediately adjacent to those symbols

Implementation constraints:
- Keep `launch_mxfp4_pack_a_fixed_raw(...)` and exact m16 workspace accounting unchanged in the first pass.
- Do not add any new B helper launch.
- Prefer consuming validated live `b_shuffle` directly.
- Replace the current worst m16-specific body costs:
  - raw row-major B stride of `3584 B` per lane
  - per-step `/224` and `%224` style scale recovery
  - scalar byte-copy pattern that wider kernels already avoid
- Prefer the same style already used in wider exact kernels:
  - vector load lower `16 B` with `i32x4`
  - zero only the unused upper half of the MFMA operand buffer
  - move scale address math to a closed-form helper or fixed constants where possible
- Keep block size at `64` and keep exact public shape constants fixed.
- Do not collapse into any serial sweep, persistent owner grid, or B temp materialization path.

Executed Task 3 result:
- Added a new experimental exact-m16 kernel body behind the Task-2 surface in `fp8-mm/submission.py`.
- The implementation keeps A-pack and workspace accounting unchanged.
- The new kernel interprets live `b_shuffle` as a no-copy row-blocked view `[n/16, (k/2) * 16]` and gathers B bytes from that layout directly, with no new per-call B temp.
- The current implementation assumption is: `shuffle_weight(..., layout=(16,16))` makes each `16 x 16` byte tile consumable through row-blocked gather `tile_base + step * 1024 + group4 * 256 + i * 16 + lane16`.
- This is now structurally implemented, but not yet correctness-validated on remote.

Fast falsifier:
- If remote test shows the transpose/gather assumption for live `b_shuffle` is wrong, kill this m16 lane immediately and pivot to `m256` rather than iterating local micro-permutations.
